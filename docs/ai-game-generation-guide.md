# AI Game Generation Guide

This document defines the required game artifact contract for AI-generated games. It is based on the observed Astrocade play model: a platform game page embeds a sandboxed iframe, injects a self-contained HTML game document, and keeps platform controls such as like, comments, favorite, share, replay, next game, create, and profile outside the iframe.

The goal is not only MVP delivery. Generated games must be compatible with a long-term Astrocade-like creation and play experience.

## 1. Target Runtime Model

Generated games must run as isolated browser games inside a platform-controlled iframe.

Required platform shape:

```text
Game detail / Play page
  Platform shell
    title, cover, author, stats, social actions
    replay, next game, create, profile navigation
  Sandbox iframe
    generated game document
```

Required iframe sandbox:

```html
<iframe sandbox="allow-scripts"></iframe>
```

The generated game must not depend on the parent React app. It must be playable inside the iframe with no access to the main app token, localStorage, cookies, database, or backend internals.

## 2. Generated Game Artifact Requirements

The primary game artifact is a self-contained HTML document.

Minimum required files in MinIO:

```text
games/{gameId}/versions/{versionNo}/index.html
games/{gameId}/versions/{versionNo}/manifest.json
```

Optional files:

```text
games/{gameId}/versions/{versionNo}/assets/*
games/{gameId}/versions/{versionNo}/thumbnail.png
games/{gameId}/versions/{versionNo}/source.json
```

Preferred MVP+ loading mode:

```text
Backend resolves MinIO object -> Web fetches game HTML -> Web injects it into iframe srcdoc
```

`index.html` must include:

- `<!doctype html>`
- `<title>{game title}</title>`
- full viewport layout
- at least one interactive game scene
- inline or referenced CSS
- inline or referenced JS
- deterministic start/restart flow
- keyboard, mouse, pointer, or touch controls
- `postMessage` events to the platform shell

Allowed game technologies:

- DOM / CSS interactive game
- Canvas 2D
- WebGL
- Three.js
- Matter.js / Cannon.js / similar browser physics libraries
- WebAudio for simple sound effects

Disallowed by default:

- backend-only game logic
- Node/Python server dependency
- direct parent window state access
- reading cookies, JWT, localStorage, sessionStorage
- calling protected Yahaha API endpoints from inside iframe
- arbitrary third-party trackers
- unbounded network requests
- eval-style dynamic execution unless explicitly generated by a trusted build step and reviewed

## 3. Manifest Contract

Every game version must have a manifest.

Recommended shape:

```json
{
  "id": "game_slug_or_uuid",
  "gameId": "uuid",
  "versionId": "uuid",
  "version": "1",
  "runtime": "iframe-srcdoc",
  "entry": "index.html",
  "documentUrl": "http://localhost:9000/yahaha-games/games/{gameId}/versions/1/index.html",
  "sandbox": ["allow-scripts"],
  "input": ["pointer", "mouse", "keyboard", "touch"],
  "communication": "postMessage",
  "assets": [
    {
      "kind": "cover",
      "url": "http://localhost:9000/yahaha-games/games/{gameId}/versions/1/assets/cover.png"
    }
  ],
  "limits": {
    "maxInitialBytes": 10485760,
    "maxTotalBytes": 20971520
  }
}
```

Runtime values:

- `iframe-srcdoc`: platform fetches HTML and injects it through `iframe.srcdoc`.
- `iframe-url`: platform sets `iframe.src` to a public or signed URL.
- `yahaha-runtime-v1`: future structured runtime that loads a JSON game definition.

The preferred runtime is `iframe-srcdoc`, because it matches the observed Astrocade-like model and gives the platform more control over loading, validation, and fallback UI.

## 4. Frontend Play Requirements

The web app must receive the following information from the backend before play:

- game ID / slug
- title
- author
- cover URL
- play count
- like / favorite / comment counts
- current version ID
- manifest URL or inline manifest
- game document URL
- sandbox policy
- runtime type

Recommended frontend flow:

```text
User opens /games/{slug}/{id}
Web calls GET /games/{id}
Web renders platform shell
User clicks Play
Web calls GET /play/{gameId}/manifest
Web fetches manifest.documentUrl from MinIO through backend proxy or signed URL
Web validates size and content type
Web sets iframe.srcdoc = fetched HTML
Web sends game_start event to backend
Game runs inside iframe
Game sends postMessage events
Web records play_events and updates visible counters
```

The platform shell owns:

- routing
- login state
- comments
- likes
- favorites
- share
- replay
- next game
- player analytics
- error fallback

The iframe game owns:

- game loop
- rendering
- local in-game state
- input handling
- score / result calculation
- pause / resume inside the game

## 5. Mouse, Keyboard, Pointer, And Touch Input

Generated games must listen for input inside the iframe document only.

Recommended input APIs:

```js
window.addEventListener("keydown", onKeyDown);
window.addEventListener("keyup", onKeyUp);
canvas.addEventListener("pointerdown", onPointerDown);
canvas.addEventListener("pointermove", onPointerMove);
canvas.addEventListener("pointerup", onPointerUp);
canvas.addEventListener("touchstart", onTouchStart, { passive: false });
canvas.addEventListener("touchmove", onTouchMove, { passive: false });
```

Rules:

- Do not attach input listeners to the parent page.
- Do not require global focus outside the iframe.
- Support pointer or touch as the default control path for mobile.
- Keyboard controls are allowed but cannot be the only input for mobile-first games.
- Prevent scroll only inside the game canvas when needed.
- Prevent default browser scrolling for game keys such as arrow keys and space.
- Keep the system cursor visible and unchanged by default.
- Do not call `requestPointerLock` unless a future game type explicitly requires it and the platform enables that sandbox permission.
- Provide visible start/restart controls inside the iframe.

## 6. Continuous Game Loop Requirements

Generated games must use browser-native loops:

```js
let running = false;
let lastTime = 0;

function loop(timestamp) {
  if (!running) return;
  const delta = Math.min((timestamp - lastTime) / 1000, 0.033);
  lastTime = timestamp;
  update(delta);
  render();
  requestAnimationFrame(loop);
}

function startGame() {
  running = true;
  lastTime = performance.now();
  requestAnimationFrame(loop);
}
```

Rules:

- Use `requestAnimationFrame`, not `setInterval`, for the main loop.
- Clamp `delta` to avoid physics explosions after tab switches.
- Provide pause/resume handling for `visibilitychange`.
- Provide replay/reset without reloading the parent page.
- Avoid infinite synchronous loops.
- Clean up event listeners if the game has an internal destroy path.

## 7. iframe to Platform Communication

Generated games must communicate with the platform through `postMessage`.

Required event format:

```js
window.parent.postMessage(
  {
    source: "yahaha-game",
    type: "game_start",
    gameId: "game-id",
    versionId: "version-id",
    payload: {}
  },
  "*"
);
```

Supported event types:

- `game_ready`
- `game_start`
- `game_pause`
- `game_resume`
- `game_score`
- `game_end`
- `game_error`
- `game_asset_error`

The parent web app must validate:

- `event.data.source === "yahaha-game"`
- known `type`
- matching `gameId`
- payload size and shape

The game iframe must not receive JWT or privileged user data.

## 8. Backend Responsibilities

The backend owns the mapping between SQL metadata and MinIO objects.

Required behavior:

```text
POST /create/jobs
  create generation_jobs row
  run static generator or selected LangGraph Agent strategy
  record project, run, TaskState, memory, and run_log indexes

Agent Publisher
  upload index.html to MinIO
  upload manifest.json to MinIO
  upload cover/assets to MinIO
  create assets rows
  create or update games row
  create game_versions row
  set games.current_version_id
  set publish_status

GET /games
  read published games from PostgreSQL
  include cover URL and aggregate counts

GET /games/{gameId}
  read game, current version, author, tags, stats

GET /play/{gameId}/manifest
  resolve current_version_id
  resolve manifest asset from assets
  resolve document asset from assets
  return manifest and playable object URLs

POST /events/play
  validate game/version
  insert play_events row
  update games.plays_count on game_start
```

Current local modes:

- `CREATE_STATIC_GENERATION=false`: default OpenAI Responses-compatible LLM generation through the selected strategy. The final output is parsed into the same `index.html` / `manifest.json` / `source.json` contract and then published through MinIO plus PostgreSQL.
- `CREATE_STATIC_GENERATION=true`: explicit deterministic backend-generated game package for local persistence testing.

LLM prompts must never receive `api_key`, `projectId`, `runId`, or `taskId`. Those values are backend indexes or secrets. Run logs may record prompt prefixes, language counts, output counts, and provider token usage for debugging and cost tracking. Invalid LLM output should fail the run instead of publishing a fallback static game.

The backend should return playable objects using database records, not guessed paths.

Correct:

```text
games.current_version_id -> game_versions.manifest_asset_id -> assets.object_key/public_url
game_versions.id -> assets(kind='bundle' or kind='generated') -> index.html object
```

Incorrect:

```text
String-concatenate MinIO path without checking database ownership/version state
```

## 9. SQL And MinIO Unified Model

PostgreSQL is the source of truth for metadata, ownership, status, and counters.

MinIO is the source of truth for binary/text game objects.

Required relationship:

```text
games
  current_version_id -> game_versions.id

game_versions
  game_id -> games.id
  manifest_asset_id -> assets.id
  source_job_id -> generation_jobs.id

assets
  game_id -> games.id
  version_id -> game_versions.id
  job_id -> generation_jobs.id
  bucket
  object_key
  public_url or signed URL
  content_type
  size_bytes
  sha256
```

Required MinIO paths:

```text
games/{gameId}/versions/{versionNo}/index.html
games/{gameId}/versions/{versionNo}/manifest.json
games/{gameId}/versions/{versionNo}/assets/*
uploads/{userId}/{jobId}/{assetId}/{filename}
```

The backend must never rely on local disk paths for published game runtime.

## 10. Counters And Play Analytics

Play analytics must be written to PostgreSQL.

Minimum `play_events`:

- `game_view`: game detail opened
- `game_start`: player starts or replays game
- `game_load_error`: platform could not load manifest/document
- `game_asset_error`: iframe reports failed asset
- `game_end`: iframe reports a completed run

Counter update rules:

- Increment `games.plays_count` only on `game_start`, not on every page view.
- Insert one `play_events` row for every accepted event.
- Store `version_id` with every play event when available.
- Allow anonymous player events.
- If user is logged in, attach `user_id`.
- Keep `likes_count` and `favorites_count` derived from `game_likes` / `game_favorites`, or update them transactionally when rows change.

Example backend transaction for play start:

```sql
INSERT INTO play_events (game_id, version_id, user_id, event_type, metadata)
VALUES (:game_id, :version_id, :user_id, 'game_start', :metadata);

UPDATE games
SET plays_count = plays_count + 1
WHERE id = :game_id;
```

## 11. AI Agent Generation Instructions

When an AI agent generates a game, it must output:

1. `index.html`: complete playable iframe-safe game document.
2. `manifest.json`: runtime metadata and object references.
3. `cover.png` or cover URL metadata.
4. `source.json`: prompt, design summary, controls, libraries, generated file list.
5. safety report: dangerous API scan, external library list, resource size summary.

The generated game must include:

- title screen or clear start affordance
- visible control hints
- mobile pointer/touch support
- replay/reset
- score, success/failure, progress, or feedback loop
- `postMessage` lifecycle events
- no dependency on parent app state

The generated game should prefer:

- one self-contained HTML document for MVP+
- Canvas 2D for simple games
- Three.js / Cannon.js for 3D physics games
- relative asset paths if external files are used

## 12. Safety And Validation Checklist

Before publishing, the backend must validate:

- `index.html` exists and is not empty.
- `manifest.json` exists and matches database IDs.
- object keys are under the expected game/version prefix.
- content type is safe: `text/html`, `application/json`, image/audio types.
- file size is within limit.
- no direct references to local machine paths.
- no references to `localStorage`, cookies, JWT, or platform secrets.
- no parent DOM manipulation beyond `postMessage`.
- no unknown external scripts unless allowlisted.
- iframe sandbox excludes `allow-same-origin` by default.

Recommended allowlist for external libraries:

- Three.js CDN
- Cannon.js CDN
- Matter.js CDN
- Google Fonts

For stronger production safety, download allowed libraries into MinIO and rewrite generated games to use first-party object URLs.

## 13. Acceptance Criteria

A generated game is valid only if:

- Home shows the game from PostgreSQL.
- Game detail page shows title, cover, author, stats, and Play.
- Play fetches manifest through backend.
- Web resolves `index.html` from MinIO metadata.
- iframe runs the game using `srcdoc` or URL sandbox.
- Player can interact with mouse/pointer/touch and, where relevant, keyboard.
- Game sends `game_ready` and `game_start`.
- Backend records `play_events`.
- `games.plays_count` increments on start.
- Replay works without navigating away.
- No secret or auth state is exposed to the iframe.
